# 记忆系统设计（讨论稿，尚未实施）

> 目标：在**不劣化回答质量**的前提下，把每次请求的「前缀」变得稳定，从而提高缓存命中率、
> 降低成本与首字延迟；同时给每个会话一份可复用的「档案」，让长对话不必每次重新压缩。
>
> 本文只做方案讨论，代码未改。文末列出需要你确认的取舍。

## 1. 现在为什么缓存命中低

DeepSeek 的上下文缓存按**前缀完全匹配**计算，命中价与未命中价差 10 倍（官方 0.2 vs 2 元/M；
硅基流动 V4.1-Flash 0.04 vs 2 元/M，差 50 倍）。也就是说：只要本次请求的前 N 个 token
和上次完全一样，这 N 个 token 就按缓存价计费。

现在每次请求的 system 是这样拼的（`src/services/assist/prompt.ts`）：

```
默认人格 + 自定义人格 + 【长期记忆】若干条 + 【更早对话的记录】摘要
```

三处都在变：

| 变化源 | 触发频率 | 后果 |
| --- | --- | --- |
| 长期记忆块 | 每 `memoryEvery`（默认 6）条回复重新抽取、增删改 | system 中段变化，后面全部失效 |
| 摘要块 | 每次压缩（滚动合并） | 变化幅度最大，通常一次就是几千 token |
| 自定义人格 | 用户修改时 | 低频但同样致命 |

再叠加 `latest_reminder`（日期/星期/地点）作为独立角色插在每条用户消息前，日期一变，
当天的第一条请求之后整段历史的前缀就都变了。

结论：**现在几乎没有可复用的前缀**——历史越长，每次都在全量重算 prefill，
这既是「贵」的原因，也是「首字慢」的主要原因（比流式本身影响大得多）。

## 2. SillyTavern 的做法，以及能借鉴什么

SillyTavern 的核心不是「记忆算法」，而是**分层装填 + 固定顺序**：

1. **人设/世界书**（低频变化，永久在 system 顶部）
2. **摘要/长期记忆**（中频变化，紧随其后）
3. **最近 N 轮原文**（高频 append，永远在尾部）
4. **本轮召回**（检索到的条目，插在最后一条用户消息之前）

它每轮都重建 prompt，但因为顺序固定、只改尾部，配合支持前缀缓存的模型时命中率很高。
我们现在的顺序是对的，问题在于**第 1、2 层变化太频繁**，把第 3 层的缓存也带崩了。

## 3. 建议的目标结构

```
[稳定区] 前置指令 + 人设 + 会话档案（世界书）        ← 一个会话内几乎不变
[半稳定区] 会话摘要（只在压缩时整体替换，不滚动微调）   ← 低频变化
[追加区] 最近 K 轮原文                              ← 只向后追加
[召回区] 本轮临时检索到的记忆条目                     ← 放最后，绝不进 system
```

关键原则：**越靠前越稳定；临时内容一律放尾部。** 召回块放在最后一条用户消息之前，
即使每轮都变，也只影响尾部几十 token，前面的缓存全部保住。

## 4. 逐项设计

### 4.1 长期记忆：从「改 system」改成「放尾部」

现在记忆写进 system，一改就毁掉整个前缀。改成：

- 记忆仍然存全量（IndexedDB），但**不再整块注入**；
- 每次请求按当前提问做一次轻量检索（字面 + 关键词打分，本地计算，不调 API），取 top 3～5 条，
  以「【相关记忆】…」的形式**拼在本轮用户消息前面**；
- 置顶（pinned）的记忆才进 system 稳定区，且用户改动置顶项时提示「会让本会话缓存失效」。

预期：记忆更新不再影响前缀；命中率提升主要来自这里。

### 4.2 会话摘要：一次性替换，不滚动微调

现在 `summarizeRounds` 是「滚动合并」：新摘要 = 旧摘要 + 新段落的重写结果，
每次压缩后 system 里的几千 token 全变。

建议改成**分段定稿**：

- 把历史按固定大小切段（例如每 8 轮 / 4000 token 一段），每段单独产出一份**不可变**的段落摘要；
- system 里放的是「段落摘要 1 … 段落摘要 N」的拼接；
- 后续压缩只**追加**新段落，旧段落一个字都不动。

这样每次压缩只让尾部多出几百 token，前面的段落摘要与 K 轮原文的缓存全部保留。

### 4.3 会话档案（per-session card）

每个会话在 token 超过阈值（建议 20000）或轮次超过 30 时，生成一份「档案」：

```yaml
主题: 明史·景泰天顺
人设: 严谨史学顾问，不臆造史料
已确定的事实: [...]      # 与项目记忆分离，只在本会话有效
时间线: [...]            # 对话中发生的事件顺序
未决问题: [...]
写作偏好: 表格优先、结论先行
```

这解决两个现实问题：

1. 从别处导入的超长历史，首次进入时压缩几十段太慢（见 4.5）；
2. 用户换设备/换会话时，可以把档案作为「前言」带走。

档案本身也是稳定区的一部分：只在用户点「重建档案」或累计新增 N 轮后才更新。

### 4.4 触发与预算

| 参数 | 现在 | 建议 |
| --- | --- | --- |
| `compressAt` | 0.8 | 0.6（更早压缩，首字更稳） |
| `keepRecent` | 20 轮 | 8～10 轮（原文太多时 prefill 本身就慢） |
| 档案生成 | 无 | 单会话 > 20K token 或 > 30 轮 |
| 记忆召回 | 全量注入 | top-k 检索，尾部注入 |

内存预算按 token 分配：稳定区 ≤ 15%，摘要区 ≤ 25%，原文区 ≤ 50%，召回区 ≤ 5%，其余留白。

### 4.5 压缩吞吐（与 1.0.11 的遗留问题相关）

现在压缩是**串行**的：6000 token 一段，`for` 循环依次调用，20 万字约 35 段 =
35 次串行请求，2–3 分钟。改进顺序：

1. **分块并行**（一次 4 段并发，仍保证每段输入 ≤ 6000 token）→ 35 段约 40 秒；
2. **断点续压**：每完成一段就落盘（`SessionAssist.segments`），中断后从下一段继续，不从头再来；
3. **进度可见**：界面已经加了「正在找回之前的对话…（3/35）」，配合并行后体验可接受。

## 5. 成本与收益（估算）

以 10 万 token 历史、每轮提问 200 token 为例：

| 方案 | 每轮未命中输入 | 每轮费用（官方 2 元/M） |
| --- | --- | --- |
| 现在（前缀全变） | 约 10 万 | 约 0.20 元 |
| 稳定前缀（命中 95%） | 约 5 千 | 约 0.013 元 |

大约 **15 倍**差距，且首字延迟会从十几秒降到 1～2 秒（prefill 变短）。

## 6. 风险与取舍

| 风险 | 说明 | 应对 |
| --- | --- | --- |
| 记忆新鲜度下降 | 尾部召回是「按需取」，可能漏掉不相关但重要的事实 | 置顶机制 + 档案里保留硬约束 |
| 段落摘要不可改 | 早期摘要若有错，会一直带着 | 提供「重写某段」入口，代价是该段之后缓存失效一次 |
| 多一次本地检索 | 纯本地打分，几毫秒，可忽略 | — |
| 与官方 `latest_reminder` 的交互 | 日期变化仍会让当天首条请求前缀变化 | 可接受（一天一次），或把日期也移到尾部 |

## 7. 需要你确认的点

1. **优先级**：先做 4.1（记忆移到尾部）+ 4.2（段落摘要），还是先做 4.5（压缩并行）？
   前者省钱、后者省时，两者不冲突但不建议一次全上。
2. **会话档案**是否要可导出、可跨会话复用（类似「角色卡」）？
3. `keepRecent` 降到 8～10 轮，是否接受？对「必须记住原话」的场景（合同、代码）可能不够。
4. 是否允许调用一次接口生成档案（约 2000～4000 token 输出），还是完全本地拼装？
5. 记忆检索要不要做本地向量化（需要 embed 模型与额外磁盘），还是先用关键词+字面打分？
