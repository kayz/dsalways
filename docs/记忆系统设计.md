# 记忆系统与上下文组装设计（第 2 轮讨论稿，未实施）

> 第 1 轮回答了「为什么缓存命中低、记忆怎么分层」。
> 第 2 轮按你的两条新要求展开：**窗口随模型动态准备**、**上下文组装最小化改动保缓存**。
> 本文所有「现状」都对着代码写过位置，方案部分未动实现。

## 0. 一句话结论

把「窗口」从**一个全局数字**改成**按当前模型算出的一张预算表**；把「组装」从**每次重拼一整段 system**
改成**五段固定顺序、各段有明确的可变性契约**。任何内容只允许在自己那一段里变，
且越靠前的段越不许变——这样每次请求相对上一次的 diff 恒定在尾部几百 token。

## 2. 设计一：动态窗口预算

### 2.1 窗口来源改为三级，默认值跟着模型走

```
有效窗口 = min(用户显式设置, 当前模型窗口)
用户未显式设置时 = 当前模型窗口（不再用全局 128K 兜底）
```

「用户显式设置」需要能区分「没填」和「填了」：现在 `contextLimit = 0` 表示没填，
正好可用——0 时取模型窗口，>0 时取小值。默认值改动对老用户是**纯收益**
（164K 模型行为不变，1M 模型不再被提前压缩）。

### 2.2 每轮请求先算一张预算表，再决定装什么

以有效窗口 `W` 为输入（数值为建议比例，可调）：

| 区 | 内容 | 预算 | 超预算时怎么办 |
| --- | --- | --- | --- |
| 输出预留 | 回复 + 思维链 | `max(模型maxOutput, 思考预留)`，R1 按 64K 上限预留，其余 16K | 不可压缩，硬性先扣 |
| 稳定区 | 前置指令 + 人格 + 会话档案 | 固定实测量，建议 ≤ 5% W | 超了提示用户精简，不自动砍 |
| 摘要区 | 段落摘要拼接 | ≤ 20% W | 触发「摘要二次压缩」（见 2.3） |
| 召回区 | 本轮检索到的记忆 + 当前信息 | ≤ 5% W | top-k 逐条减到够 |
| 原文区 | 最近 K 轮原文 | 剩余全部 | 从最早的开始丢，丢掉的进摘要 |

两条触发线分开（解决「每轮都压」），**已拍板定为 60% / 40%**：

- **压缩触发线**：总量 > 60% W 才动手；
- **压后目标水位**：一次压到 ≤ 40% W，给后面留出增长空间，长对话变成「攒一段、压一次」。

W 是**当前模型的有效窗口**，所以同一份对话在 V4.1-Flash（1M）下可能完全不压缩，
切到 V3.2（164K）立刻触发压缩——阈值不需要另写规则，换模型后自动跟着变。
这正是「按模型动态调整」的落点：**不是给每个模型配一套参数，而是所有参数都从 W 推导**。

### 2.3 模型切换时的窗口迁移

| 切换方向 | 风险 | 策略 |
| --- | --- | --- |
| 大窗 → 小窗（如 V4.1-Flash → R1） | 1M 攒下的摘要 + 原文可能直接超 164K | 发送前重算预算：先砍原文区（丢更早轮次进摘要），摘要区仍超 20% 才需要**摘要二次压缩**（把若干段旧摘要压成一段，走内部 1M 摘要器）。**已拍板：必须弹窗确认，不自动做**，文案见 2.4；用户取消则回退模型选择（切换延迟到确认后才真正生效） |
| 小窗 → 大窗（R1 → V4.1-Flash） | 无 | **不回填、不展开**。已压成摘要的轮次保持摘要，只有新对话利用大窗口。展开回填会让整段前缀变化，纯亏缓存 |
| 同档互切（flash ↔ pro） | 无 | 什么都不动 |

二次压缩的产物**作为新段落追加**，旧段落保留在本地存档（不注入请求），需要时可回查。

### 2.4 压缩提示与确认弹窗（文案按「外行能懂」写）

你要求「压缩时要有明确提示」+「弹窗内容让外行看懂」。现状只有一个进度条
「正在找回之前的对话…（已整理 x/y 段）」，它**不解释为什么突然变慢**。
按压缩原因分三种文案，全部避开 token／上下文／缓存／前缀这些术语：

| 触发原因 | 形式 | 文案 |
| --- | --- | --- |
| 水位到 60%（常规） | 输入框上方进度条（沿用现有 `CompressNotice`） | 「正在整理更早的对话…（已整理 2/5 段）」+ 小字「第一次整理会慢一点，之后就快了。聊天记录不会丢，也不会改变最近的对话」 |
| 切到窗口更小的模型，需要额外丢轮次 | 同上，但换标题 | 「为了让新模型接着聊，正在整理更早的对话…（2/5 段）」+ 小字「这个模型一次能读到的内容比之前少，整理完就能继续」 |
| 摘要仍超预算，需要二次精简 | **弹窗确认，不自动执行** | 见下 |

**弹窗文案（定稿草案）**

> 标题：换个模型，要先整理一下旧对话
>
> 正文：你刚选的模型一次能读到的内容比较少，装不下这段聊天积累的全部记录。
> 为了让对话继续，需要把很久以前的内容整理成一份简要笔记。
>
> 整理大约几十秒，**不会删除你的聊天记录**，也不会改动最近聊过的内容。
> 整理过程中会产生一点点额外费用（通常几分钱）。
>
> 按钮：`现在整理` / `先不换，用回原来的模型`

关键约束（写进实现时不要破）：

1. **切换延迟生效**：弹窗出现时通道与模型还没真正落盘；点「先不换」要完整回退到上一个模型，
   不能出现「界面显示旧模型、实际已切到新通道」；
2. 弹窗只在这一种情况出现，常规压缩不打断用户；
3. 二次精简一旦确认，界面明确提示「本次整理后，接下来第一次发送会稍慢」（对应缓存失效一次），
   但不出现「缓存」二字。

## 3. 设计二：组装协议（最小化改动）

### 3.1 五段固定顺序，各段签下「可变性契约」

```
请求 = [S1 稳定区] + [S2 摘要区] + [M 原文区 messages] + [T 尾部区] + [本轮提问]
```

| 段 | 内容 | 允许的变化 | 变化频率 | 变了损失多少缓存 |
| --- | --- | --- | --- | --- |
| S1 稳定区 | 前置指令、人格、会话档案 | 只能用户手动改；改前提示「本会话缓存将失效一次」 | 一次会话 0~1 次 | 全段 |
| S2 摘要区 | 段落摘要 1…N | **只追加**，已落盘段落一个字不改 | 攒一段压一次 | 仅新增部分未命中，旧段全保 |
| M 原文区 | 最近 K 轮原文（各轮自带冻结的时间快照） | 只尾部追加；头部只在压缩时整段移除（与 S2 追加同帧发生） | 每轮追加 | 追加天然命中 |
| T 尾部区 | 召回记忆 top-k、**本轮**当前信息 | 随便变 | 每轮 | 只影响尾部几百 token |
| 本轮提问 | 用户输入 | 每轮必变 | 每轮 | 同上 |

核心规则一句话：**任何高频变化的内容都不许进 S1/S2；任何低频内容都不许放 T。**

### 3.2 对照现状要改的三件事

1. **记忆搬家**：`buildSystemPrompt` 不再收 `facts`；`runtime.ts` 里已写好的 `selectFacts`
   从「只算统计」改成真输出，top-k 结果以「【相关记忆】」拼进 T 段（最后一条用户消息前）。
   置顶记忆仍留 S1，但改动置顶要弹缓存失效提示。
2. **摘要改分段定稿**：`summarizeRounds` 的滚动合并改为「每段独立摘要、落盘后不可变」，
   S2 是段落拼接；压缩事件 = S2 追加一段 + M 头部移除对应轮次，**同一帧完成**，
   其余字节不动。旧摘要在迁移时作为「第 0 段」整体保留，不重写。
3. **R1 特例**：`inlineSystem` 把 S1+S2 并进首条 user 时，拼接规则不变、顺序不变，
   只是落点从 system 字段变成消息体——缓存语义一致，不需要单独策略。

**历史时间快照不改**（原第 4 点已撤销）：它是冻结的，不动它才符合「最小化改动」。理由见 3.4。

### 3.3 度量先行，每步都有数字

现在 `usage` 里已经有 `cache_read_input_tokens`（官方与硅基流动都映射了），
但只埋在日志里。建议第 0 步先做：

- 每轮请求把 `命中率 = cache_read / prompt_tokens` 写进 `timing.log`，
  会话调试面板显示「本轮缓存命中 x%」与近 10 轮曲线；
- 之后每一步改造（记忆搬家 / 分段摘要 / 预算表）都用这个指标验收，
  **命中率没升的改动不合并**。

### 3.4 第 4 点核查结论：历史时间快照**不改**

你问「如果是旧对话，为什么会变日期/地点？」——**答案是不会变，我原来的论证错了。**

代码事实（三处）：

| 位置 | 行为 |
| --- | --- |
| `store.ts:1113-1116` | 每条回复生成时把 `createLatestReminder()` 的结果写进 `reply.latestReminder`；**续写沿用原回答的快照**（`prepared.prefix.latestReminder`），不重新取时间 |
| `reply.ts:324` | 遍历历史时用的是 `reply.latestReminder`，即那条回复存下来的**固定字符串**；`appendReminder` 只在与上一轮不同时插入一条 |
| `reply.ts:327` | 只有**本轮** `latestReminder` 是现算的，插在最后一条用户消息之前（尾部） |

由此得到三条结论：

1. 跨天、改地点、换语言，**都不会改写任何一条历史消息的快照**——它们躺在消息对象里，是常量；
2. 真正变化的只有尾部那一条当前信息，**前缀完全不受影响**；
3. 更根本的是：**即使历史中间插了块，只要内容固定，它本身就是稳定前缀的一部分，照样命中缓存**。
   「历史中间有块所以破坏前缀」这个说法在原理上就不成立，我把「插入位置」和「插入内容变化」混为一谈了。

**唯一会让历史中间变化的情形**：重新生成某条旧回复时，`store.ts` 给新 reply 存一份**当天**的快照。
但这不算额外损失——重新生成本来就会替换整条回复正文，缓存必然失效一次，
快照那几十 token 不是新增的失效源；且这是用户主动触发的低频操作。

**导入的历史会话**：归档不保存 `latestReminder`（`history/README.md`），导入后的旧轮次没有快照，
只有新提问按当前设置生成一条——同样不存在「旧快照变化」。

**结论：第 4 点撤销，历史快照维持现状，一行代码都不改。**

这反而更贴合「最小化改动」原则：为一个不存在的缓存问题去重写历史消息，
等于凭空制造一次全量失效，还会丢掉「明天交方案」这类相对时间的参照。
分段摘要里照旧保留日期（摘要器规则 1 已要求），只是不再需要
「把时间参照搬进摘要头部」这套补偿方案——它补偿的是一个不存在的问题。

## 4. 实施顺序（每阶段独立可验收）

| 阶段 | 内容 | 风险 | 验收指标 |
| --- | --- | --- | --- |
| 0 | 命中率埋点 + 面板显示 | 无 | 能看到当前真实命中率基线 |
| 1 | 动态窗口预算（2.1 默认值 + 2.2 预算表 + 双水位线 60/40）+ 2.4 分原因的压缩提示 | 低，不动组装结构 | 1M 模型不再提前压缩；换小窗模型时提示能说明原因；长对话压缩次数明显下降 |
| 2 | 记忆搬家到 T 段（`keepRecent` 定稿 8~10、关键词打分不上向量库） | 中，召回质量靠 top-k | 命中率升；回答不遗忘置顶事实 |
| 3 | 分段定稿摘要 + 模型切换迁移（2.3）+ 2.4 弹窗确认与「先不换」回退 | 中，涉及存量摘要迁移 | 压缩后旧段缓存仍命中；大→小窗不超窗；取消切换后模型与通道完整回退 |
| 4 | 会话档案（第 1 轮的 4.3，S1 的新成员） | 低 | 超长导入会话首压时间下降 |

不建议跳步：1 是 2/3 的前提（预算表决定各段大小），2 比 3 简单且收益直接。
