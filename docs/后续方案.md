## 二、数据只存在本地的问题：可选同步方案

现状：数据在 IndexedDB 里，卸载、重装系统、换机器都会丢；手机和电脑之间无法接续。DeepSeek 不开放对话历史的云端读写接口，chat-demo 的导入导出也是本地 ZIP，所以同步只能自己做。

按「成本 / 工作量 / 能不能真正解决」排序：

| 方案 | 谁出钱 | 多端接续 | 工作量 | 说明 |
| --- | --- | --- | --- | --- |
| **A. 加密快照 + 用户自己的同步盘** | 用户（已有的网盘） | 半自动 | 0.5 天 | 改动后防抖 5 分钟，把全库打成 AES-GCM 加密 ZIP 写到用户选的目录（OneDrive / 坚果云 / NAS / 移动硬盘），滚动保留 N 份；启动时若发现快照比本地新，提示一键恢复。**解决「丢了找不回」，不解决「同时用」** |
| **B. 阿里云 OSS / 腾讯 COS 直传** | 用户自己开账号 | 半自动 | 1 天 | 客户端用 STS 临时凭证直传，不需要自己的服务器。但用户要实名、开 Bucket、配 RAM 子账号，对「不熟悉软件的人」比自己装网盘还麻烦 |
| **C. Cloudflare Workers + R2 + D1** | 我们（免费额度够用） | 真同步 | 2–3 天 | 端到端加密：密钥由用户口令派生，服务端只见密文。R2 免费 10 GB 存储、无出网流量费，Workers 免费 10 万次/天。**但免费额度要绑国际信用卡**，且国内访问 `*.workers.dev` 不稳，得挂自定义域名 |
| **D. 换 LobeChat / Open WebUI + 自建 Postgres** | 用户（VPS 或 NAS） | 真同步 | 重做 | 现成的多端方案，但会把这里的压缩、记忆、引导全部推倒重来，不建议 |
| **E. 交给第三方笔记软件** | 用户 | 靠人 | 0 | 把每个会话导出 Markdown 丢进语雀/Notion。适合归档，不适合继续聊 |

**建议路径：先做 A，把「丢了找不回」这条兜住；真需要多端再上 C。**

### Cloudflare 要不要用户自己申请

要。Cloudflare 没有「代注册」这回事，做 C 方案的话是我们（或用户）去开一个账号、绑卡、建 R2 Bucket 和 D1 库，再把 `wrangler` 配置里的账号 ID 填进代码。**用户不需要申请**——他们只面对我们的客户端。

麻烦的点在别处：

- R2 免费额度需要绑一张国际信用卡（Visa/Master，国内双币卡多数能用，纯银联不行）；
- `*.workers.dev` 在国内访问不稳定，正经用要绑自己的域名并备案（境内解析）；
- 数据出境：如果服务端存的是密文、且不持有密钥，合规压力小很多，但「服务器在境外」这件事本身要跟用户讲清楚。

### 为什么不直接用阿里云 OSS 做我们的同步后端

对象存储只能存文件，做不了「按会话增量合并」。要支持两端同时改同一个会话，需要一个能跑逻辑的地方（Workers / 函数计算）和一份索引（D1 / RDS）。纯 OSS 方案只能退化成「整库快照覆盖」，跟 A 方案能力一样，却多了一笔流量费（外网下行约 0.5 元/GB）和一堆账号配置。

**如果决定要自建后端，阿里云函数计算 + OSS + Tablestore 是可行的**，代价是比 Cloudflare 贵一点（没有免费额度）、但国内访问稳、备案和发票都顺。这是「要不要在中国大陆正经运营」的分岔口，不是技术选型问题。

## 三、转发别家 API 并收通道费：可行，但不是技术问题

技术上完全可行，架构也不复杂：

```
客户端 → 我们的网关（Anthropic 兼容 /v1/messages）→ 上游（硅基流动/百炼/火山/OpenRouter…）
```

网关要做的事：协议转换（Anthropic ↔ OpenAI）、key 池与轮换、按用户限流、用量计量、余额扣减、失败重试。现成的开源件就能干大半：**LiteLLM Proxy** 或 **one-api / new-api**（后者带用户、充值、额度、日志的后台）。

### 需要服务器吗

需要，但不需要很贵的：

- 一台 2C4G 的轻量云服务器（国内约 ¥60–100/月）足够几百人日常用；
- 或者纯 Serverless（函数计算 / Workers），按调用计费，人少时几乎不花钱；
- 真要商用还要带宽与备案：境内域名必须 ICP 备案，才允许对外提供 HTTP 服务。

### 真正的门槛不在服务器

| 事项 | 说明 |
| --- | --- |
| 上游条款 | 各家 API 的 ToS 基本都禁止「未授权转售」。做小范围自用/朋友共享没事，做成对外收费的生意，账号被封是常态风险 |
| 定价与账单 | token 成本随模型和上下文波动，做预付余额要先解决「余额不够时优雅降级」和「用到一半断流怎么退」 |
| 合规 | 面向公众提供生成式 AI 服务要按《生成式人工智能服务管理暂行办法》做大模型登记/备案，并落实内容审核与 AI 生成内容标识；收费还要有营业执照与发票 |
| 内容安全 | 一旦「我们转发」，内容责任就从上游转到我们身上，必须开 `safety_check` 并留存日志 |
| 客服与退款 | 用户量一上来，这是最耗人的部分 |

**结论**：自己用、给朋友用，LiteLLM + 一台小服务器 + 自己发的卡密就够了；要当生意做，成本和风险都在合规与运营，不在技术。这一版不做。

### 顺带解决的「接别家模型」

即使不做转发，客户端也应该能接别的通道（V3.2 / R1 / GPT / Kimi / 自建 vLLM）。改动很小：

1. `API_ORIGIN` 现在是构建期常量 `__API_ORIGIN__`，要改成从设置读；
2. 设置里加「接口地址 + 模型名 + 协议」三项；
3. Electron 的 CORS 兜底从「只给 `api.deepseek.com` 补头」改成「只给带 `Origin: app://porter` 的请求补头」；
4. 每个通道配一张**能力开关表**——我们的请求带 `deepseek_web_search`、`deepseek_read_url`、thinking `signature`、Files API 这些 Anthropic 扩展，第三方网关多半不认，接过去会退化成「纯文本聊天」。

大约半天工作量，性价比很高，建议排在 A 方案之后。

## 四、用户自己的历史管理

不依赖任何服务端也能做的，按优先级：

| 能力 | 状态 |
| --- | --- |
| 导入官方导出 ZIP（覆盖式） | 已有 |
| 导出全部会话为 ZIP（v3 格式，可再导入） | 已有（上游自带） |
| 按会话导出 Markdown / JSON | 待做，约 2 小时 |
| 全库加密快照 + 手动恢复 | 待做（A 方案的一半） |
| 会话置顶 / 标签 / 全文搜索 | 待做，搜索用 IndexedDB 索引，不需后端 |
| 定期提醒「距上次备份 N 天」 | 待做，跟 A 方案一起 |

其中「加密快照」是唯一能解决「丢了完全找不回」的，其余都是顺手。
