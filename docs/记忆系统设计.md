# 记忆系统与上下文组装设计（第 2 轮讨论稿，未实施）

> 第 1 轮回答了「为什么缓存命中低、记忆怎么分层」。
> 第 2 轮按你的两条新要求展开：**窗口随模型动态准备**、**上下文组装最小化改动保缓存**。
> 本文所有「现状」都对着代码写过位置，方案部分未动实现。

## 0. 一句话结论

把「窗口」从**一个全局数字**改成**按当前模型算出的一张预算表**；把「组装」从**每次重拼一整段 system**
改成**五段固定顺序、各段有明确的可变性契约**。任何内容只允许在自己那一段里变，
且越靠前的段越不许变——这样每次请求相对上一次的 diff 恒定在尾部几百 token。

## 2. 设计一：动态窗口预算

### 2.1 窗口来源改为三级，默认值跟着模型走

```
有效窗口 = min(用户显式设置, 当前模型窗口)
用户未显式设置时 = 当前模型窗口（不再用全局 128K 兜底）
```

「用户显式设置」需要能区分「没填」和「填了」：现在 `contextLimit = 0` 表示没填，
正好可用——0 时取模型窗口，>0 时取小值。默认值改动对老用户是**纯收益**
（164K 模型行为不变，1M 模型不再被提前压缩）。

### 2.2 每轮请求先算一张预算表，再决定装什么

以有效窗口 `W` 为输入（数值为建议比例，可调）：

| 区 | 内容 | 预算 | 超预算时怎么办 |
| --- | --- | --- | --- |
| 输出预留 | 回复 + 思维链 | `max(模型maxOutput, 思考预留)`，R1 按 64K 上限预留，其余 16K | 不可压缩，硬性先扣 |
| 稳定区 | 前置指令 + 人格 + 会话档案 | 固定实测量，建议 ≤ 5% W | 超了提示用户精简，不自动砍 |
| 摘要区 | 段落摘要拼接 | ≤ 20% W | 触发「摘要二次压缩」（见 2.3） |
| 召回区 | 本轮检索到的记忆 + 当前信息 | ≤ 5% W | top-k 逐条减到够 |
| 原文区 | 最近 K 轮原文 | 剩余全部 | 从最早的开始丢，丢掉的进摘要 |

两条触发线分开（解决「每轮都压」）：

- **压缩触发线**：总量 > 60% W 才动手；
- **压后目标水位**：一次压到 ≤ 40% W，给后面留出增长空间，长对话变成「攒一段、压一次」。

### 2.3 模型切换时的窗口迁移

| 切换方向 | 风险 | 策略 |
| --- | --- | --- |
| 大窗 → 小窗（如 V4.1-Flash → R1） | 1M 攒下的摘要 + 原文可能直接超 164K | 发送前重算预算：先砍原文区（丢更早轮次进摘要），摘要区仍超 20% 再做**摘要二次压缩**（把若干段旧摘要压成一段，走内部 1M 摘要器）。这是一次性事件，界面明示「为适应当前模型，正在整理更早的记录」，并提示本次缓存会失效 |
| 小窗 → 大窗（R1 → V4.1-Flash） | 无 | **不回填、不展开**。已压成摘要的轮次保持摘要，只有新对话利用大窗口。展开回填会让整段前缀变化，纯亏缓存 |
| 同档互切（flash ↔ pro） | 无 | 什么都不动 |

二次压缩的产物**作为新段落追加**，旧段落保留在本地存档（不注入请求），需要时可回查。

## 3. 设计二：组装协议（最小化改动）

### 3.1 五段固定顺序，各段签下「可变性契约」

```
请求 = [S1 稳定区] + [S2 摘要区] + [M 原文区 messages] + [T 尾部区] + [本轮提问]
```

| 段 | 内容 | 允许的变化 | 变化频率 | 变了损失多少缓存 |
| --- | --- | --- | --- | --- |
| S1 稳定区 | 前置指令、人格、会话档案 | 只能用户手动改；改前提示「本会话缓存将失效一次」 | 一次会话 0~1 次 | 全段 |
| S2 摘要区 | 段落摘要 1…N | **只追加**，已落盘段落一个字不改 | 攒一段压一次 | 仅新增部分未命中，旧段全保 |
| M 原文区 | 最近 K 轮原文 | 只尾部追加；头部只在压缩时整段移除（与 S2 追加同帧发生） | 每轮追加 | 追加天然命中 |
| T 尾部区 | 召回记忆 top-k、日期/地点等当前信息 | 随便变 | 每轮 | 只影响尾部几百 token |
| 本轮提问 | 用户输入 | 每轮必变 | 每轮 | 同上 |

核心规则一句话：**任何高频变化的内容都不许进 S1/S2；任何低频内容都不许放 T。**

### 3.2 对照现状要改的四件事

1. **记忆搬家**：`buildSystemPrompt` 不再收 `facts`；`runtime.ts` 里已写好的 `selectFacts`
   从「只算统计」改成真输出，top-k 结果以「【相关记忆】」拼进 T 段（最后一条用户消息前）。
   置顶记忆仍留 S1，但改动置顶要弹缓存失效提示。
2. **摘要改分段定稿**：`summarizeRounds` 的滚动合并改为「每段独立摘要、落盘后不可变」，
   S2 是段落拼接；压缩事件 = S2 追加一段 + M 头部移除对应轮次，**同一帧完成**，
   其余字节不动。旧摘要在迁移时作为「第 0 段」整体保留，不重写。
3. **当前信息归队**：`latest_reminder` 不再随历史消息逐条插入，只保留**本轮一条**、放 T 段。
   历史消息里的旧 reminder 快照不再注入（它们本来就是当天临时信息，没有长期价值）。
4. **R1 特例**：`inlineSystem` 把 S1+S2 并进首条 user 时，拼接规则不变、顺序不变，
   只是落点从 system 字段变成消息体——缓存语义一致，不需要单独策略。

### 3.3 度量先行，每步都有数字

现在 `usage` 里已经有 `cache_read_input_tokens`（官方与硅基流动都映射了），
但只埋在日志里。建议第 0 步先做：

- 每轮请求把 `命中率 = cache_read / prompt_tokens` 写进 `timing.log`，
  会话调试面板显示「本轮缓存命中 x%」与近 10 轮曲线；
- 之后每一步改造（记忆搬家 / 分段摘要 / 预算表）都用这个指标验收，
  **命中率没升的改动不合并**。

## 4. 实施顺序（每阶段独立可验收）

| 阶段 | 内容 | 风险 | 验收指标 |
| --- | --- | --- | --- |
| 0 | 命中率埋点 + 面板显示 | 无 | 能看到当前真实命中率基线 |
| 1 | 动态窗口预算（2.1 默认值 + 2.2 预算表 + 双水位线） | 低，不动组装结构 | 1M 模型不再提前压缩；长对话压缩次数明显下降 |
| 2 | 记忆搬家到 T 段 | 中，召回质量靠 top-k | 命中率升；回答不遗忘置顶事实 |
| 3 | 分段定稿摘要 + 模型切换迁移（2.3） | 中，涉及存量摘要迁移 | 压缩后旧段缓存仍命中；大→小窗不超窗 |
| 4 | 会话档案（第 1 轮的 4.3，S1 的新成员） | 低 | 超长导入会话首压时间下降 |

不建议跳步：1 是 2/3 的前提（预算表决定各段大小），2 比 3 简单且收益直接。

## 5. 需要你拍板的点（比第 1 轮收敛后只剩这些）

1. **默认窗口放开**：没设过窗口的老用户，官方通道从 128K 恢复到 1M——意味着更晚压缩、
   单次请求更贵但次数更少。接受？（推荐接受，总费用因缓存命中反而降）
2. **双水位线参数**：60% 触发 / 压到 40%，还是更保守的 70% / 50%？（前者省钱后者保原文）
3. **摘要二次压缩**：大窗切小窗时允许自动做（有提示），还是只提示、由用户点确认？
4. **历史 reminder 快照不再注入**：旧日期/地点对回答基本无价值，但严格说是「少给了模型信息」，确认可弃？
5. 第 1 轮遗留：`keepRecent` 降到 8~10 轮、记忆检索先用关键词打分（不上向量库）——维持原建议？
